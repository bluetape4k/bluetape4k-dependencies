# Cross-repository publication POM gate

## Context

The central catalog adoption train verified catalog ownership, downstream
Gradle configuration, builds, and resolved graphs. It deliberately allowed a
repository-local alias to remain versionless when central dependency management
supplied the version.

That rule is valid for Gradle authoring, but the train did not inspect the Maven
POM generated by each library publisher. A downstream build could therefore
resolve correctly while its published dependency-management entry omitted a
version. Maven consumers then failed while building the effective model.

## Decision or Finding

Catalog authority and publication metadata are separate contracts. Every
catalog train that can affect library publishers must prove both:

- Gradle resolves the candidate catalog and dependency graph;
- every generated POM is structurally valid and Maven can build its effective
  model.

Every dependency-management entry, including a BOM import, requires a version.
A regular dependency may omit its version only when it is covered by a
versioned entry in the same POM or by a versioned imported BOM. Maven then
verifies that the imported BOM actually manages that dependency coordinate.

## Outcome

`scripts/verify-publication-poms.py` configures all nine library publishers
against the candidate central catalog, runs their publication POM generation
tasks, audits every generated POM, and validates all effective models in one
temporary Maven reactor. `bluetape4k-experimental` remains in the catalog
adoption audit but is excluded from this gate because it is not a publisher.

Gradle version-catalog publications use `toml` packaging, which Maven does not
recognize as a lifecycle. Their original POM is audited unchanged; only the
temporary Maven-reactor copy normalizes `toml` to `pom` so dependency-model
validation can proceed.

The gate removes only prior `build/publications/*/pom-default.xml` files before
regeneration, compares the configured publishers with the managed registry and
live snapshot-publish workflows, and rejects publication POM profiles. Profiles
are fail-closed because inactive Maven profiles would otherwise escape the
default effective-model reactor.

## Verification

- `python3 -m unittest tests/test_verify_publication_poms.py tests/test_ci_catalog_governance.py`
- `scripts/verify-publication-poms.py --workspace .. --summary`
- 9 publisher repositories, 175 freshly regenerated POM files, 46,009 dependency entries, and 175
  Maven effective models passed.

## Future Guidance

Do not interpret “this train does not publish” as “Maven validation is N/A.” If
the candidate catalog can affect a downstream publisher, generated publication
metadata is part of the train's Definition of Done. Run the exact-candidate
gate with `--repository-map` when worktrees or candidate branches are involved.
